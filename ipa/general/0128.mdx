# IPA-128: Stability Levels

<Guidelines>

<Guideline id="IPA-128-must-declare-stability-level" enforcement="advisory">

Every API version **must** declare an associated stability level that states the
maturity, expected pace of change, and support policy for the API.

</Guideline>

</Guidelines>

## Guidance

<Guidelines>

<Guideline id="IPA-128-must-document-stability-level" enforcement="advisory">

API resources **must** indicate their stability level in their documentation.

</Guideline>

<Guideline id="IPA-128-must-use-defined-stability-level" enforcement="advisory">

API resources **must** use one of these stability levels: **preview**,
**stable**, **deprecated**, and **sunset**.

</Guideline>

</Guidelines>

### Preview

A **preview** API resource undergoes rapid iteration based on user feedback.

<Guidelines>

<Guideline id="IPA-128-may-restrict-preview-audience" enforcement="advisory">
  A **preview** API resource **may** be available only to a selected group of
  users.
</Guideline>

<Guideline
  id="IPA-128-may-break-preview-without-version"
  enforcement="advisory"
>
  A **preview** API resource **may** introduce breaking changes without
  requiring a new version ([IPA-120](0120.mdx)).
</Guideline>

<Guideline id="IPA-128-must-provide-preview-feedback-mechanism" enforcement="advisory">

For a **preview** API resource, a feedback mechanism **must** be established for
users to report issues and suggest improvements.

</Guideline>

<Guideline
  id="IPA-128-must-not-expect-preview-stability"
  enforcement="advisory"
>
  Consumers **must not** have any expectation of stability from a **preview**
  API resource.
</Guideline>

<Guideline
  id="IPA-128-should-not-use-preview-in-production"
  enforcement="advisory"
>
  Consumers **should not** use a **preview** API resource in production.
</Guideline>

</Guidelines>

### Stable

A **stable** API resource is production-ready and fully supported.

<Guidelines>

<Guideline id="IPA-128-must-make-stable-available-to-all" enforcement="advisory">

A **stable** API resource **must** be available to all users.

</Guideline>

<Guideline id="IPA-128-must-not-break-stable-without-version" enforcement="advisory" dependsOn={["IPA-128-must-use-defined-stability-level"]}>

A **stable** API resource **must not** introduce breaking changes without
requiring a new version ([IPA-120](0120.mdx)).

</Guideline>

<Guideline id="IPA-128-must-keep-stable-backwards-compatible" enforcement="advisory">

A **stable** API resource **must** maintain backwards compatibility
([IPA-116](0116.mdx)) to ensure ongoing reliability.

</Guideline>

<Guideline
  id="IPA-128-must-support-stable-until-migration"
  given="spec"
  enforcement="advisory"
>
  A **stable** API resource **must** remain supported until its announced sunset
  date, which **must** be communicated well in advance, unless otherwise agreed
  between API provider and customers.
</Guideline>

</Guidelines>

### Deprecated

A **deprecated** API resource is still supported but is on its way to becoming
**sunset**.

<Guidelines>

<Guideline
  id="IPA-128-may-stop-deprecated-backwards-compat"
  enforcement="advisory"
>
  A **deprecated** API resource **may** stop receiving new functionality, but
  **must** keep working as documented until it is **sunsetted**.
</Guideline>

<Guideline id="IPA-128-must-declare-replacement-decision" given={["operation", "schema", "parameter"]} enforcement="review" effort="check">

A **deprecated** API resource, field, or parameter **must** state whether it has
a replacement:

1. If it has a replacement, the documentation **must** name it and provide a
   migration plan that explains how consumers move to it. The replacement may be
   another element in the same version (for example, another field), the same
   operation in another version, or a different resource or endpoint.
2. If it has no replacement, the documentation **must** state that none exists
   and that the element will be removed in a future version.

The documentation **should** also state why the element is being deprecated.

<Guideline.Details>

<Example.Correct>

```yaml
components:
  schemas:
    Invoice:
      type: object
      properties:
        total:
          type: number
        amount:
          type: number
          deprecated: true
          description: >-
            Deprecated: use `total` instead. Read `total` and stop reading or
            sending `amount`. It is deprecated because both fields always held
            the same value. `amount` remains supported in this version and is
            removed only in a new version.
```

<Example.Reason>
  The deprecated field names its replacement, explains the migration, gives the
  reason for the deprecation, and says how long it stays supported.
</Example.Reason>

</Example.Correct>

<Example.Correct>

```yaml
paths:
  /invoices:
    get:
      operationId: listInvoices
      parameters:
        - name: legacyFormat
          in: query
          deprecated: true
          description: >-
            Deprecated: ignored, and will be removed in a future version. There
            is no replacement. It is deprecated because the server always uses
            the default format.
          schema:
            type: boolean
```

<Example.Reason>
  The deprecated parameter has no replacement, so the description says so
  explicitly, gives the reason, and states that it will be removed.
</Example.Reason>

</Example.Correct>

<Example.Incorrect>

```yaml
components:
  schemas:
    Invoice:
      type: object
      properties:
        amount:
          type: number
          deprecated: true
```

<Example.Reason>
  The field is deprecated but says nothing about a replacement, so consumers
  cannot tell whether there is a migration path or the field is simply going
  away.
</Example.Reason>

</Example.Incorrect>

</Guideline.Details>

</Guideline>

<Guideline id="IPA-128-must-transition-deprecated-to-sunset" given="operation" enforcement="review" effort="check">

A **deprecated** API resource or version **must** be **sunsetted** within an
established timeframe ([IPA-120](0120.mdx)). Deprecated fields and parameters
have no independent sunset date and are removed only in a new API version
([IPA-116](0116.mdx)).

<Guideline.Details>

<Example.Correct>

```yaml
paths:
  /orders/{orderId}:
    get:
      operationId: getOrder
      deprecated: true
      responses:
        "200":
          headers:
            Sunset:
              schema:
                type: string
                format: date-time
```

<Example.Reason>
  The deprecated operation announces a sunset date, so consumers know when it
  will stop working and can plan their migration.
</Example.Reason>

</Example.Correct>

<Example.Incorrect>

```yaml
paths:
  /orders/{orderId}:
    get:
      operationId: getOrder
      deprecated: true
```

<Example.Reason>
  The operation is deprecated but no sunset date is established, so consumers
  have no timeframe to migrate within.
</Example.Reason>

</Example.Incorrect>

<Workflow>
  <Workflow.Step>Find every deprecated operation or version.</Workflow.Step>
  <Workflow.Step>
    Confirm each carries a sunset date, or is covered by the version's defined
    timeframe.
  </Workflow.Step>
  <Workflow.Step>
    Confirm deprecated fields and parameters have no independent sunset date.
  </Workflow.Step>
  <Workflow.Step>
    Report any deprecation without an established timeframe.
  </Workflow.Step>
</Workflow>

</Guideline.Details>

</Guideline>

<Guideline id="IPA-128-must-provide-deprecation-header" given="operation" enforcement="automatable">

A **deprecated** API resource **must** return the Deprecation HTTP response
header ([RFC 9745](https://datatracker.ietf.org/doc/rfc9745/)) to signal to
consumers that the resource is deprecated.

<Guideline.Details>

The header is added to responses at runtime for the API version being served. In
the version-specific specification, the operation for that version is marked
`deprecated: true`. The header's date comes from the version's deprecation date,
which is not recorded in the specification.

</Guideline.Details>

</Guideline>

<Guideline id="IPA-128-must-provide-sunset-header" given="operation" enforcement="automatable">

A **deprecated** API resource **must** return the Sunset HTTP response header
([RFC 8594](https://datatracker.ietf.org/doc/html/rfc8594)) to signal to
consumers when it will be **sunsetted**.

<Guideline.Details>

Record the sunset date as `x-sunset`. In the version-specific specification, an
operation whose version is being removed is marked `deprecated: true` and
carries `x-sunset`. The header is added to responses at runtime for that
version; it is not declared as a response header in the specification.

<Example.Correct>

```yaml
paths:
  /orders:
    get:
      operationId: listOrders
      deprecated: true
      x-sunset: "2099-01-01"
      responses:
        "200":
          content:
            application/vnd.example.2023-01-01+json:
              x-xgen-version: "2023-01-01"
              schema:
                $ref: "#/components/schemas/PaginatedOrders2023"
```

<Example.Reason>
  The operation for the version being removed is marked `deprecated: true` and
  records its sunset date, so the runtime can emit the Sunset header for it.
</Example.Reason>

</Example.Correct>

<Example.Incorrect>

```yaml
paths:
  /orders:
    get:
      operationId: listOrders
      deprecated: true
      responses:
        "200":
          content:
            application/vnd.example.2023-01-01+json:
              x-xgen-version: "2023-01-01"
              schema:
                $ref: "#/components/schemas/PaginatedOrders2023"
```

<Example.Reason>
  The operation is deprecated but records no sunset date, so the runtime cannot
  emit the Sunset header and consumers do not know when it stops working.
</Example.Reason>

</Example.Incorrect>

</Guideline.Details>

</Guideline>

<Guideline id="IPA-128-should-migrate-from-deprecated" enforcement="advisory">
  Where a replacement exists, consumers **should** migrate to it during the
  deprecation period. They **may** keep using the deprecated resource until its
  sunset date.
</Guideline>

</Guidelines>

### Sunset

A **sunset** API resource is no longer supported.

<Guidelines>

<Guideline id="IPA-128-must-deprecate-before-sunset" given="operation" enforcement="review" effort="reason">

A **stable** API resource or version **must not** be **sunsetted** without first
being **deprecated**. Deprecated fields and parameters follow the lifecycle of
the version that contains them. For version-level rules, see
[IPA-120](0120.mdx).

<Guideline.Details>

<Example.Correct>

```yaml
paths:
  /orders/{orderId}:
    get:
      operationId: getOrder
      deprecated: true
      responses:
        "200":
          headers:
            Sunset:
              schema:
                type: string
                format: date-time
```

<Example.Reason>
  The operation is deprecated with an announced sunset date, so it is sunsetted
  only after a deprecation phase consumers can act on.
</Example.Reason>

</Example.Correct>

<Example.Incorrect>

```yaml
paths:
  /orders/{orderId}:
    get:
      operationId: getOrder
      responses:
        "410":
          description: Gone.
```

<Example.Reason>
  The operation is already gone (410) with no deprecation phase, so consumers
  had no warning and no migration window.
</Example.Reason>

</Example.Incorrect>

<Workflow>
  <Workflow.Step>Compare the spec against the prior version.</Workflow.Step>
  <Workflow.Step>
    For each removed or sunsetted element, confirm the prior version marked it
    deprecated with an announced sunset date.
  </Workflow.Step>
  <Workflow.Step>
    Confirm deprecated fields and parameters follow their version's lifecycle.
  </Workflow.Step>
  <Workflow.Step>
    Report any element that was sunsetted without a deprecation phase.
  </Workflow.Step>
</Workflow>

</Guideline.Details>

</Guideline>

<Guideline id="IPA-128-must-return-410-for-sunset" given="operation" enforcement="automatable">

A **sunset** API resource **must** return
[410 GONE](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/410).

</Guideline>

<Guideline id="IPA-128-must-migrate-from-sunset" enforcement="advisory">
  A **sunset** API resource no longer works, so consumers **must** have migrated
  to a replacement, where one exists, by its sunset date.
</Guideline>

</Guidelines>
